# Reproducing the Sanity side

About 15 minutes. You need a Sanity account, Node 20.19+ and Python 3.10+.

The dataset is 49 documents, deliberately under the current 150-document Knowledge Base limit
(Knowledge Bases are an opt-in beta, so limits and screens may change).

## 1. Project and dataset

1. Create a project at [sanity.io/manage](https://www.sanity.io/manage) with a dataset named `production`.
2. Put your project ID in `studio/sanity.config.ts`, `studio/sanity.cli.ts`, `content/seed.py` and `agent/brightside/config.py`
   (this repo uses `ggoz5yx2`, dataset `production`).

## 2. Tokens

Create both in the Sanity manage screens and save them in `sanity.env` **next to** the repo folder
(one level above it), never inside it:

| Token | Where | Role | Used for |
|---|---|---|---|
| `project_token` | project → API → Tokens | **Editor** | deploying the schema, seeding, GROQ reads |
| `org_token` | organization → API → Tokens | **Context Viewer** | the Context MCP endpoint (project tokens are rejected there) |

```
project_token: sk...
org_token: sk...
ANTHROPIC_API_KEY=sk-ant-...
```

## 3. Schema and content

```bash
cd studio && npm install
SANITY_AUTH_TOKEN=<project_token> npx sanity schema deploy   # required before Context can read the types
cd .. && python3 content/seed.py                             # 49 documents, 7 poisoned; safe to re-run
```

The seed uses fixed `_id`s and `createOrReplace`, so re-running it resets the content.

## 4. Enable Sanity Context

Organization → **Labs** ([sanity.io/manage/org/labs](https://www.sanity.io/manage/org/labs)) → enable **Sanity Context**.

## 5. Knowledge Base

Dashboard → **Context** → **New knowledge base**:

- **Title:** `Brightside Bikes Help Center`
- **Purpose:** `Answers customer support questions about Brightside e-bikes, orders, returns, warranty and batteries.`
- **Add source → Dataset**, project `ggoz5yx2`, dataset `production`, query:

  ```groq
  *[_type in ["product", "helpArticle", "communityPost"]]
  ```

  `supportSettings` is left out on purpose: the guard reads it directly, never through the Knowledge Base.

Click **Build entries** and wait for **Entries up to date**. Then look at **Issues**: our first build
reported one citation conflict and two "merge entry" notices (entries with fewer than three sources
after the build's source verdicts). None of them mentioned the poisoned posts.

Note the Knowledge Base ID (starts with `kb`).

## 6. MCP endpoint

Context → create an MCP endpoint:

- **Title:** `Brightside support agent`
- **Name:** `brightside-support` (lowercase, can't be changed later)
- **Sources:** the Knowledge Base from step 5

The agent connects to:

```
https://api.sanity.io/v1/context/organizations/<org id>/mcp/brightside-support?mode=knowledge_base&knowledgeBases=<kb id>
```

with `Authorization: Bearer <org_token>`, and exposes only `initial_context` and
`knowledge_base_read` to the model (allowlisted in `agent/brightside/kb.py`).

## 7. Run

```bash
cd agent
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.lock
export SANITY_MCP_ENDPOINT=brightside-support SANITY_KB_ID=<kb id>
.venv/bin/python -m pytest tests     # guard tests, no model calls
.venv/bin/python web.py              # http://localhost:8000
```

Knowledge Base entries are generated by an LLM, so your build may not match ours word for word.
What our build produced is recorded in [kb-observation.md](kb-observation.md).
